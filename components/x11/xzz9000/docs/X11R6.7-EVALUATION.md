# Moving Xzz9000 from X11R6.3 to X11R6.7/6.8: evaluation

2026-11-07. The question: should the AMIX X server and libraries (today
X11R6.3 with the Xzz9000 DDX, A3000 + Z3660 RTG) move to X11R6.7, the X.Org
monolithic tree that descends from XFree86 4.4? If so, how?

**Short answer: not now, and not as a whole tree.** Most of what R6.7 adds does
nothing on this machine, or costs more than it gives. The 060 draws at
10-26 MB/s, scanout is RGB565 whatever the depth (see
[DEPTH-24-32-EVALUATION.md](DEPTH-24-32-EVALUATION.md)), there is no DRM
kernel, and GL already runs on the client side and on core 1. Only two
features have real value:

1. **RandR**, a live change of resolution, which the planned CDE display panel
   needs.
2. **Render**, the base for anti-aliased Xft text.

Both are cheaper to get without a new tree:

- **RandR**: backport the RandR 1.1 extension (one directory, MIT licence)
  into the R6.3 server, plus a resize hook in the Xzz9000 DDX. That takes
  about 1 to 1.5 weeks.
- **Xft**: build libXrender, freetype, fontconfig and Xft as components.
  Xft2 draws through core protocol when the server has no Render. That takes
  about 1 week, but first measure whether anti-aliased text is fast enough on
  the 060.

A full R6.7/6.8 server is about 5-8 weeks of work. It is only worth it later,
and then most likely as a kdrive server, whose acceleration, VRAM pixmaps,
RandR and Xv hooks match this card. Section 6 has that plan.

Nothing in this report was measured on the box, and nothing was downloaded.
The facts come from the Xzz9000 tree, the amix-userland components, the
memory notes and the sibling depth report. Statements about the R6.7/6.8
sources are from knowledge of those releases, and section 7 lists the ones to
check after unpacking.

Paths: the brief's `~/Sources/usr-amix/xzz9000-z3/` no longer exists. The
server is `amix-userland/components/x11/xzz9000` (its `src` links to
`private/xzz9000/src`), and the libraries are `components/x11/x11r6.3`.

---

## 1. Where we are (R6.3 Xzz9000)

- **Server.** `src/xc/programs/Xserver/Xzz9000`: 1.44 MB text, 235 KB data,
  70 KB bss. It is built with gcc-cross-amix 2.7.2.3 (`build.sh`) from the
  user's R6.3 tree, the 14 amix-z3660rtg `x11/patches`, and 6 local patches
  (copywindow-order, paintwindow-tile, pattern-fill, bell, putimage-move16,
  soft3d-swap). MIT-SHM is switched on with a sed in `amix.cf`.
- **DDX.** `hw/amix` (input, keyboard, mouse, bell, console) and
  `hw/amix/rtg/zz9000` (3274 lines). It is a **custom DDX, not cfb**: the
  ScreenRec and GC ops are its own, depth-1 GCs go to mfb, and pixels are
  `unsigned short` everywhere. The card's blitter is used through
  `ZZ9KIOC_BLITS`. PutImage uses move16, and the soft3D swap does a VRAM to
  VRAM blit. Pixmaps live in host memory.
- **Mode.** It is fixed when the server starts (`-mode WxH`, a table of 8
  modes in `zz9000hw.c`). The kernel's `ZZ9KIOC_SETMODE` can switch at any
  time.
- **Extensions in the server.** SHAPE, MIT-SHM, BIG-REQUESTS, SYNC, XC-MISC,
  SECURITY, XTEST, XInputExtension, XKEYBOARD, DOUBLE-BUFFER, RECORD,
  Multi-Buffering, LBX, XC-APPGROUP and ZZ9K-SOFT3D. There is no Render,
  RandR, Xv, XFixes, Damage, Composite or GLX.
- **Libraries.** R6.3 libX11/Xt/Xext/Xmu/Xaw/ICE/SM/Xi/Xtst/Xp are built
  shared with gcc 14 as `libX*.so.7` in `/usr/x11r6/lib`, with `.pc` files
  and `libXtInherit.a` (`x11r6.3/files/build-shared.sh`). Motif 2.3.8,
  CDE 2.2.4a, Mesa 3.1/18.3, TinyGL, NetSurf, ffplay/vplay, sdl2-amix and
  Grafx2 all link against them. Getting those libraries right took the hard
  part of the shared-library work: R_68K_COPY class records
  (`amix-fix-data-relocs`), `_XtInherit`, link stubs and the ld.so.1 NEEDED
  order.

## 2. What R6.7/6.8 brings, and what it is worth here

X.Org 6.7.0 (April 2004) is XFree86 4.4 RC2 relicensed. 6.8 (September 2004,
last 6.8.2 in February 2005) adds Composite, Damage, XFixes and XEvIE. When
"R6.7" is said below, 6.8.2 is the better pick: it has the same structure,
two more releases of fixes, and the extensions that 6.7 lacks.

| feature | in 6.7 / 6.8 | value on A3000 + Z3660 | why |
|---|---|---|---|
| **RandR 1.1** (resize, rotate, refresh) | both | **high** | The CDE display panel needs it. The DDX must supply the set-config hook in every case (2.1) |
| **Render** | both | medium | It is the base of anti-aliased Xft text. The server side is in `fb` (fbpict), and its cost on the 060 is not yet known (2.2) |
| **Xft2 / fontconfig / freetype** | client libs | medium | Anti-aliased fonts for Motif 2.3.8 (`--enable-xft`), CDE, NetSurf and new programs. It works without Render through core protocol |
| fb (generic framebuffer, any depth) | both | medium as a code base | It could replace much of `zz9000draw.c`. Depth itself buys nothing: scanout is 565 (sibling report) |
| 24/32-bit depth | both | **none** | The HDMI path is 16-bit 565 in every mode |
| XVideo (Xv) | both | low to medium | A standard API for the core 1 overlay plane. vplay/ffplay already drive the overlay directly; Xv would add clipping/colour-key and other clients (2.3) |
| XFixes | 6.8 | low | Cursor images and regions. Only needed under Damage/Composite |
| Damage | 6.8 | low | Only matters for a VNC-style server or a compositor |
| Composite | 6.8 | **negative** | Redirecting every window to an off-screen pixmap means a full copy on every change: hopeless at 10-26 MB/s |
| GLX (indirect, software libGLcore) | both | **negative** | Rendering in the server with Mesa on the 060 is slower than today's client-side Mesa over MIT-SHM and the soft3D/zzgl core 1 path |
| DRI | both | none | It needs DRM kernel drivers. AMIX has none, and the card has no 3D engine for DRM |
| XKB | both | none new | R6.3 already has XKB (`BuildXKB YES`). R6.7's xkb data is newer (more layouts); the de layout works today |
| Xutf8* API in libX11 | 6.7 libX11 | low to medium | R6.3 Xlib lacks `Xutf8DrawString` and friends. Some ports need `#ifdef` paths |
| kdrive (TinyX: Xfbdev, Xvesa, …) | in the tree | **interesting** | A small server with KAA acceleration hooks, VRAM pixmap migration, RandR resize and an Xv framework (section 4) |
| XFree86 DDX + loader | both | none | It is built for PCI cards and `.o`/ELF driver modules. None of that applies to a Zorro RTG card behind `/dev/zz9000` |

### 2.1 RandR: what it really takes

The RandR extension in DIX (`programs/Xserver/randr/`, randr.c and
mirandr.c) only does the protocol: the list of sizes, the events, and the
connection-block edit. The actual resize is the DDX's `rrSetConfig`. For a
custom DDX like ours that hook is the same work on R6.3 and on R6.7:

- Set the mode with `ZZ9KIOC_SETMODE` and re-map (or keep) the framebuffer.
  Wait for the blitter first.
- Update `pRTG->width/height/pitch` and `pScreen->width/height/mmWidth/
  mmHeight`, and call `ModifyPixmapHeader` on the screen pixmap.
- Resize the root window and its clip. XFree86 does this in
  `xf86SetRootClip`, kdrive in `KdSetRootClip`, about 100 lines each, built
  on `miValidateTree` / `ResizeChildrenWinSize`, which R6.3 has.
- Clamp the cursor and mouse limits (amixMouse/`bp.width`), and repaint.

The XFree86 DDX in 6.7/6.8 only shrinks inside the virtual size it started
with (the pitch stays the same). kdrive's Xfbdev really sets a new mode. A
real mode set is what the Z3660 needs, since a smaller mode at a fixed pitch
may not scan out right.

**Note for the CDE display panel session.** dtwm (CDE 2.2.4a) and mwm do not
listen for `RRScreenChangeNotify`. After a resize the front panel and icons
stay where they were, possibly off-screen. The panel has to restart the
window manager (`f.restart`) or move the front panel itself. That holds on
R6.3+RandR and on R6.7 alike.

### 2.2 Render and anti-aliased text on the 060

- **Server side.** Render's composite code is `fb/fbpict.c`. The custom DDX
  could use it unchanged if its screen pixmap and host pixmaps are fb-shaped:
  linear, stride in 32-bit units, with `devPrivate.ptr` and `devKind`.
  Today's 16-bit linear VRAM and host pixmaps probably qualify, but the
  stride padding needs a check. Every composite of an A8 glyph onto RGB565
  is a read-modify-write per pixel.
- **Reads from the RTG framebuffer have never been measured** (only writes:
  10.6 MB/s long, 26 MB/s move16). Measure that first.
- **Rough cost.** A full 80x24 dtterm page is about 1900 glyphs of about
  7x13 pixels, so about 170 k blended pixels. At 20-40 cycles per pixel that
  is 40-90 ms on the 060, plus the VRAM reads. That is usable for a
  terminal, but visibly slower than core fonts. A Render composite on core 1
  (the GPU plan) would remove it.
- **Without server Render.** Xft2's core fallback (xftcore.c) does
  GetImage, blends on the client side, then PutImage. Over the local socket
  that is slow, but it needs **no server change**. MIT-SHM GetImage helps.
  It is good enough to try AA fonts in NetSurf or a Motif test program on
  today's server.

### 2.3 XVideo and the core 1 overlay

An Xv adaptor in the DDX would advertise one port (YUV420/YUY2 or the
decoder's own format), position the Z3660 overlay at the window, and use a
colour key for clipping. That would give ffplay `-vo xv`, mplayer-style
clients and the CDE desktop a standard path. But vplay already drives the
overlay registers itself, and the core 1 decode path bypasses X on purpose
(core1-lwip-plan). So Xv is a convenience, not a gain, and R6.3 lacks it.
The Xv DIX code (`Xext/xvmain.c`, `xvdisp.c`, about 4 k lines) could also be
backported if it is ever wanted.

## 3. Porting cost of an R6.7/6.8 server to AMIX SVR4 2.1c/m68k

### 3.1 Config (imake)

R6.7 still uses imake with `Imake.cf`/`*.cf`, so the R6.3 `amix.cf` (91
lines) carries over with these changes:

- AMIX detection in `Imake.cf`/`imakemdep.h`, which CDE's tree already has
  done once (src-cde commits).
- `host.def` for the cross build: `BuildServersOnly YES`, `XorgServer NO`,
  `XnestServer`/`XVirtualFramebufferServer NO`, `BuildXInputExt YES`,
  `BuildGlxExt NO`, `BuildXF86DRI NO`, `BuildFreeType NO` for the server,
  `HasShm YES`, and `ConnectionFlags -DTCPCONN -DUNIXCONN` (no LOCALCONN: the
  xtrans SVR4 named-stream and pts variants are not needed).
- A cross build: a host imake/makedepend bootstrap and `imakecpp.sh`, as in
  `build.sh` today. 6.7 builds more host tools on the way (mkg3states,
  makestrs, xkbcomp for the data if built, bdftopcf for fonts). With
  `BuildServersOnly` only a few are needed.
- About **2-3 days**, based on the R6.3 and CDE experience.

### 3.2 OS layer

- `os/` (WaitFor.c select, connection.c via xtrans, utils.c, io.c) is
  POSIX/SVR4 code that also builds on Solaris 2.x and UnixWare.
- AMIX specifics to carry over from R6.3: `select`, `gettimeofday`,
  `shmsys` and the others from the `libc.a` stub archive (libc.so.1 does not
  export them), `-lsocket -lnsl` (the hosts variant, see the libsocket trap),
  `-ldbm -lscreen`, `-Dvfork=fork` (the server forks xkbcomp; AMIX vfork
  shares memory) and `NEED_STRCASECMP`.
- 6.7's `os/` also wants `snprintf`/`vsnprintf` (Xprintf, log.c) and
  probably `strlcpy` replacements. Xorg's own `os/` versions or libamixc99
  cover those.
- Input stays the AMIX `/dev/screen` raw-key/mouse path (SIOCACTIVATE,
  SIM_RAWKEY). It moves unchanged into the new DDX.
- About **2-4 days**.

### 3.3 Toolchain

- **gcc 2.7.2.3** (today's server compiler): R6.7/6.8 expects gcc 2.95 or
  later. `__inline__` use, variadic macros in places, `long long` in Render
  and fb, and some `__FUNCTION__` would each mean a stack of local patches.
  Not recommended.
- **gcc14-cross-amix**: the libX*.so.7, Motif, CDE and Mesa are already
  built with it, and the server is userland, so it may use it. gcc 14 turns
  implicit declarations, implicit int, int-conversion and
  incompatible-pointer-types into errors. Old X code needs
  `-std=gnu89 -fcommon -Wno-error=implicit-function-declaration
  -Wno-error=implicit-int -Wno-error=int-conversion
  -Wno-error=incompatible-pointer-types`, guarded to gcc 14 only
  (toolchain-specific-fixes).
- Known gcc 14 m68k traps apply: the fold-mem-offsets and a0/d0 fixes are
  already in, and doubles are aligned to 4 rather than 8, so check structs
  passed to libc. No `-fPIC` for the server, so the GOT bug does not arise.
- Compiling R6.3 Xzz9000 itself with gcc 14 would be a useful first step
  in any plan: it separates compiler problems from R6.7 problems.

### 3.4 Size and memory

- A 6.8 server with dix, os, mi, fb, Xext, xkb, render, randr, miext/shadow
  and damage, plus our DDX and no loader, should come to about **2-3 MB
  text**, against 1.44 MB today. kdrive is about the same or a little
  smaller (it has no XKB in 6.8). Add font code (libfont with freetype
  backend if wanted, about 0.5 MB more).
- With 256-272 MB of RAM that is no problem. Neither is the larger resident
  heap (Render glyph caches, fb pixmaps). The real limits stay CPU and
  memory bandwidth, not RAM.
- Start-up time: the server binary loads through ld.so.1 as today. A static
  server avoids the libc PLT cost.

### 3.5 Mapping the Xzz9000 DDX onto 6.7

Three ways, from least to most change:

| way | what | keeps | effort |
|---|---|---|---|
| **A. Carry the custom DDX over** | hw/amix as a standalone DDX (like hw/sun), with the ZZ9000 ScreenRec/GC ops forward-ported to 6.7 DIX. Render is added by calling `fbPictureInit` on fb-shaped pixmaps (2.2) | all fast paths, all local fixes | 1.5-2 weeks |
| **B. Rebase the DDX on fb** | `fbScreenInit` on the mapped VRAM; wrap the GC ops (as XAA does) only for blitter fills/copies, move16 PutImage, the soft3D swap and the cursor. About 1600 lines of `zz9000draw.c` become fb | the fast paths; pattern/tile/CopyWindow bugs gone with fb's tested code | 2-3 weeks |
| **C. A kdrive server "Xzz9000"** | KdCardFuncs for `/dev/zz9000`, KdMouse/KdKeyboard drivers for `/dev/screen`, KAA hooks (PrepareSolid/Solid, PrepareCopy/Copy) → `ZZ9KIOC_BLITS`, VRAM pixmap migration, RandR via `randrSetConfig` → `ZZ9KIOC_SETMODE`, optional Xv adaptor | blitter, RandR, Xv framework built in; move16 PutImage must be wrapped again; no XKB | 3-4 weeks |

The DIX API differences R6.3 → 6.7 that touch A and B:

- `CreateScreenResources`, `devPrivates` (still index arrays in 6.7/6.8, so
  this is easy), `PaintWindowBackground/Border` (still present),
  `miInitializeBackingStore`, and font glyph functions (the DDX uses the mi
  glyph code).
- Changes in `ScreenRec` fields and the `miScreenInit` arguments. The DDX
  does not use `miScreenInit`, so it fills the vector itself and must add the
  new members.

C is the most attractive in the long run:

- KAA keeps pixmaps in the 128 MB RTG area, where the blitter can reach them.
  Today every pixmap copy is done by the 060 in host memory.
- RandR resize and an Xv adaptor have a ready place.

C's risks:

- kdrive 6.8 has no XKB. CDE and Motif work with core keymaps, but the
  keymap work in `cde-amix/keymap` needs checking.
- kdrive in the monolithic tree was a side branch. Its imake support for a
  non-Linux OS must be checked (section 7).

## 4. Client side

The X protocol is unchanged across R6.3 → R6.7. An R6.7/6.8 server serves
R6.3 clients, and new clients built against newer libraries run against
the R6.3 server, as long as they check for extensions (Xrandr, Xrender,
Xft and Xv do).

### 4.1 Option 1: keep the R6.3 libraries, add new ones as components (recommended)

- Leave libX11/Xt/Xext/Xmu/Xaw/ICE/SM `.so.7` as they are. Nothing that
  depends on them (Motif, CDE, Mesa, TinyGL, NetSurf, ffplay/vplay,
  sdl2-amix, Grafx2, amixsysmon) has to be rebuilt or tested again.
- Add one component per library, each from its own pristine upstream
  tarball plus `patches/`, with a manifest and licence, oi-userland style:

  | component | upstream | needs |
  |---|---|---|
  | x11/randrproto, x11/renderproto | protocol headers (X.Org modular 7.0 era) | – |
  | x11/libxrender | libXrender 0.9.0.x (X11R7.0) | x11r6.3 libX11 headers (GetReq/_XReply/extutil exist in R6.3) |
  | x11/libxrandr | libXrandr 1.1.x (X11R7.0) | libxrender, xext |
  | library/freetype | freetype 2.x (recent, no X) | zlib, libpng (have) |
  | library/fontconfig | fontconfig 2.x | freetype, expat (have) |
  | x11/libxft | libXft 2.1.x | xrender, fontconfig, freetype |
  | (later) x11/libxv, libxfixes | X11R7.0 versions | xext |

  Pick **old** library versions. Newer libXrender, libXrandr and libXft
  call libX11 1.6 functions (`_XEatDataWords`, `_XGetRequest`) that R6.3
  lacks. Each needs the usual AMIX handling: amix-mkshlib, `amix-got-check`,
  `amix-fix-data-relocs` on libraries that export data, `.pc` files, link
  stubs on the box, and native pkg-config.
- Motif 2.3.8 can then be rebuilt with `--enable-xft` as a separate step,
  only once AA text speed is known (2.2).

### 4.2 Option 2: move the client libraries to R6.7 too

- R6.7 libX11 is an ABI superset of R6.3 (it adds Xutf8 and XKB/locale
  fixes). Swapping `libX11.so.7` in place would keep binaries running in
  principle.
- But every trap from 2026-11-01 (COPY relocs, `_XtInherit`, NEEDED order,
  link stubs) must be re-proved against the new libraries, and the whole
  desktop tested again.
- Xt/Xaw/Xmu change little in 6.7, so there is no gain there.
- Worth doing only if a client needs Xutf8 or the newer Xlib i18n. **Not
  recommended now.**

### 4.3 Package layout

- The monolithic tree fits the model the way x11r6.3 does today: **one**
  component (`x11/x11r6.8`) with pristine tarballs, `patches/`, and one
  manifest that `provide`s several libraries.
- That is allowed, but it is the weakest fit with "every library its own
  component" (CLAUDE.md, package-manifests). With Option 1 the R6.8 tree
  would only be the server component (`x11/xzz9000` built from it). New
  client libraries come from the X.Org modular tarballs, one component each.
- If the whole X stack is ever replaced, **X11R7.x modular** (2005 onward:
  each library, proto, app and xorg-server its own tarball, autotools, `.pc`
  files) matches the amix-userland model far better than 6.7/6.8. The
  sections above apply to it too: xorg-server 1.1-1.4 still has kdrive and
  the same DIX. Its cost is autotools cross configuration (configure.mk
  exists) and later C99 code, which gcc 14 handles well.

## 5. Options and estimates

| option | gives | effort | risk |
|---|---|---|---|
| **0. Stay on R6.3, as is** | – | 0 | the CDE panel can only restart X with a new `-mode` (no live change) |
| **1. R6.3 + RandR backport + DDX resize** | live resolution change, `xrandr`, a standard API for the CDE panel | **1-1.5 weeks** | small: one new extension, one DDX hook, tested mode by mode |
| **2. + Xft/fontconfig/freetype/Xrender client libs** | AA text through core fallback; later Render | +1 week (libs) | AA text speed on the 060 unknown |
| 2b. + Render backport into R6.3 (render/ + fb/fbpict + mipict, needs fb-shaped pixmaps) | fast(er) AA text | +1.5-2 weeks | fb pieces in an R6.3 server: hybrid code to maintain |
| 3A/3B. X.Org 6.8.2 server, custom DDX carried or rebased on fb | Render, RandR, Xv framework, XFixes; fb code | **5-7 weeks** (config 0.5 w, OS + build 1 w, DDX 1.5-3 w, extensions/RandR hook 1 w, desktop retest 1 w) | gcc 14 on old code; every CDE/Motif/GL client to retest against a new server |
| 3C. X.Org 6.8.2 kdrive Xzz9000 | as 3 + VRAM pixmaps (blitter for pixmap copies), RandR/Xv ready | **6-8 weeks** | kdrive build on a non-Linux OS; no XKB |
| 4. Full R6.7 stack incl. client libs | Xutf8 | 3 + 2-3 weeks | re-proving all shared-lib traps |

## 6. Recommendation and step plan

**Do option 1 now. Do option 2 as soon as fonts are wanted. Keep 3C as a
later project, and only start it if KAA's VRAM pixmaps or Render on core 1
turn out to matter.** Do not do option 4.

### Step plan for options 1 and 2 (on R6.3)

1. **RandR backport.**
   - Take `programs/Xserver/randr/` (randr.c, mirandr.c, randrstr.h) and
     `include/extensions/randr*.h` from X.Org 6.8.2. A single small file
     set is enough; it does not need the whole tree. Its licence is MIT.
     Keep it as `patches/00xx-randr-backport.patch` against pristine R6.3
     in the xzz9000 component.
   - Register it in `mi/miinitext.c` and build it in
     `Xserver/Imakefile`.
   - Port the DIX calls it uses (`SecurityLookupWindow`, resource types,
     `WriteEventsToClient`, screen privates). All exist in R6.3.
2. **DDX hook.** Add `rtgRandRGetInfo` (the 8-mode table, extended with
   `zz_video_modes.h` modes that fit VRAM, all 60 Hz, no rotation) and
   `rtgRandRSetConfig`:
   - wait for the blitter, then `ZZ9KIOC_SETMODE`;
   - update `pRTG`, the screen size, the screen pixmap header and the root
     clip (copy the logic of kdrive's `KdSetRootClip`);
   - adjust the cursor and mouse limits and the VT console size;
   - repaint the root.
   - Pick the physical size (mm) from the panel's real DPI.
3. **Client.** `x11/libxrandr` and `x11/libxrender` components (old
   versions, 4.1), plus `xrandr` 1.0.x as an app component. Hand the API to
   the CDE display panel session, with the dtwm caveat (2.1).
4. **Test on the box** (with the user's OK, via `amix-box`, never while a
   player runs, one change at a time):
   - `xrandr -q`, then each size from 640x480 to 1920x1080 and back;
   - CDE login, dtterm, Motif, GL (gears over MIT-SHM, soft3D swap), and
     ffplay at each size;
   - VT switch (Alt+F) after a resize.
5. **Fonts (option 2).** Add the components library/freetype,
   library/fontconfig and x11/libxft, then a small Xft test program.
   - Measure the AA text speed with the core fallback on the box.
   - Measure framebuffer read speed (bench/vrambw read case), because it
     decides whether a Render backport (2b) or a core 1 Render path is the
     next step.
6. **Before any R6.8 work (option 3):** build today's R6.3 Xzz9000 with gcc
   14 (guarded flags). That separates compiler trouble from tree trouble.

### Step plan if option 3C is chosen later

1. Download X11R6.8.2 (needs the user's OK, see below). Create the component
   `x11/xorg-server-68` with the pristine tarball and SHA-256. Unpack it and
   check the facts in section 7.
2. `amix.cf` + `host.def` for `BuildServersOnly`, kdrive only, gcc 14 flags.
   Bootstrap imake on the host. Build dix/os/mi/fb/render/randr/Xext without
   a DDX: link errors only for the DDX entry points.
3. Write `hw/kdrive/zz9000`:
   - card and screen init on `/dev/zz9000`, with the mode table;
   - `/dev/screen` keyboard and mouse drivers (from amixKbd/amixMouse/
     amixKeyMap), plus the bell;
   - KAA solid and copy through `ZZ9KIOC_BLITS`;
   - wrapped PutImage with move16;
   - the ZZ9K-SOFT3D extension;
   - RandR set-config.
4. Run it beside the R6.3 server on the box (as `/opt/amix/bin/Xzz9000-68`,
   chosen by `startx-z3`, with the user's OK). Test CDE, Motif, GL, ffplay,
   NetSurf and the VT switch. Only then make it the default.
5. Optional: an Xv adaptor for the overlay, and Render on core 1 (core1 GPU
   plan).

### Status of option 1 (2026-11-07, tested on the A3000)

**Server.** `local-randr.patch` and its `build.sh` step:

- `randr.c` and `randrstr.h` are taken pristine from
  `distfiles/xorg-server-1.0.2.tar.bz2`, and `randr.h`/`randrproto.h` from
  `randrproto-1.1.2`. Both tarballs are checked against `SOURCES.sha256`.
- The patch fits `randr.c` to the R6.3 DIX: the EventSwapPtr typedef,
  `extern WindowTable`, and casts on xrealloc.
- It adds `ScreenRestructured` to `dix/events.c` and registers the
  extension (`BuildRandR`, `-DRANDR`).
- **DDX side** in `hw/amix/rtg/rtgRandR.c`:
  - `rtgRRGetInfo` offers the sizes of the mode table at 60 Hz with
    rotation 0. The table is now the Z3660 driver's 17 modes. Sizes taller
    than 1100 rows are left out, because soft3D's back buffer starts at row
    1100.
  - `rtgRRSetConfig` turns the root clip off, calls `ZZ9000SetSize`
    (SETMODE, check with GETFBINFO, clear), updates the ScreenRec, and turns
    the root clip back on. That exposes every window.
  - R6.3's `miValidateTree` has no REGION_BROKEN path, unlike xorg's. So
    `rtgSetRootClip` empties the borderClips of the root's children when the
    screen goes off, and gives the root's clipList the whole screen when it
    comes back. Without this the windows kept their old clips: the screen
    stayed black and blits past the new edge made the kernel refuse the
    blitter (EINVAL).
  - `ZZ9000SetSize` flushes the blit queue before SETMODE. A refused blit
    batch is logged record by record.
- The new server has 9.7 KB more text. `nm` shows only RandR symbols added.

**Clients.** New components, built, staged, and in the cross sysroot:
`x11/randrproto`, `x11/renderproto`, `x11/libxrender` (libXrender.so.1, patch
0001: R6.3 `region.h`), `x11/libxrandr` (libXrandr.so.2, patch 0001: R6.3
Xlibint.h has no include guard) and `x11/xrandr`. All undefined symbols
resolve to the R6.3 libX11/Xext or to libc.

**Test on the box.** `xrandr -q` lists 15 sizes. 1920x1080 to 1280x720 and
back redraws every window, and the card blitter stays on.

**Known limits:**
- A running soft3D or zzgl program keeps its old stride and must be
  restarted after a resize.
- dtwm and mwm do not follow the new size (2.1).
- Only the default `unix.z3-z3l` kernel has been read. The VT-switch kernel's
  console was not checked against a mode change.
